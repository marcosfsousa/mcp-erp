# Specification deviations

One row per deliberate departure from a normative statement — `MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT` — in a specification or RFC this exhibit claims to follow.

**This register points; it does not decide.** Every row is already decided in an ADR, and the *Reasoning* column is the pointer. A deviation with no ADR behind it is not yet decided and does not belong here yet.

**Add the row in the same commit as the ADR that creates the deviation.** Reconstructing this set by re-reading the ADR trail at write-up time is how one gets missed.

**Scope is normative statements only.** Departures from this project's own constraints — map constraint #11's floating-major exception for GitHub Actions, for instance — are not specification deviations and stay where the constraint lives.

| 1 | **RFC 8707 §2** — the authorization server "SHOULD audience-restrict issued access tokens to the resource(s) indicated by the `resource` parameter" | `SHOULD` | Keycloak does not honour `resource`, so it does not audience-restrict on that basis. Our clients send `resource` regardless, because the specification requires it independently of server support, and the **resource server's own audience check is the load-bearing control**. | Inherited from the chosen dependency rather than chosen by us — [keycloak#41526](https://github.com/keycloak/keycloak/issues/41526) closed *superseded, not implemented*; the replacement is milestoned after the build window. Survivable because the two specifications do not meet in our favour by accident: RFC 8707 §2 is only a `SHOULD` on the authorization server, while the MCP resource server is under a hard `MUST` to reject anything not issued for it. | [ADR-0005 §Deviations 1](adr/0005-the-authorization-server-is-a-dependency-not-a-deliverable.md) |
| 2 | **RFC 8414 §2 and §3** — an issuer identifier is "a URL that uses the 'https' scheme", and the well-known path "MUST use the 'https' scheme". **RFC 9728 §1.2** — a resource identifier is "a URL that uses the https scheme". | `MUST` | Under Compose both use plain HTTP: issuer `http://keycloak:8081/realms/{realm}`, resource identifier `http://localhost:8080/mcp`. No carve-out for localhost, loopback or development exists in either document. | Offline reproducibility. No certificate authority issues a certificate for `keycloak:8081`, and a self-signed authority makes certificate trust a setup step for every third-party client — against map constraint #5 and ship line #8. **A property of the local harness, not of the design**: a Cloud Run deployment (#10) is genuinely HTTPS and demonstrates the conformant form with no trick. | [ADR-0005 §Deviations 2](adr/0005-the-authorization-server-is-a-dependency-not-a-deliverable.md) |
| 3 | **MCP Security Best Practices `2026-07-28` §State Handle Hijacking** — servers "SHOULD use secure, non-deterministic handles generated with secure random number generators. Avoid predictable or sequential identifiers that could be guessed by an attacker." | `SHOULD` | Requisition identifiers are sequential and legible (`req_0104`). The clause's companion `MUST NOT` — never treat possession of a handle as authentication — **is** honoured, and asserted twice: indistinguishable `not_found` on the read path, and a refused write that leaves state unmodified. | Following it would delete the proof of the half we do honour. ADR-0002 made indistinguishability the load-bearing control; unguessable identifiers mean the probe scenario can no longer *guess* a foreign identifier and must be handed one, turning a demonstrated defence into an asserted one. What is traded away is defence in depth, stated rather than hidden. | [ADR-0003 §Identifiers are sequential and legible](adr/0003-the-schema-is-the-policy-functions-argument-list.md), [ADR-0010](adr/0010-the-clause-decides-the-row-the-removal-decides-the-split.md) |
